# Глобальный план рефакторинга XMSGi Studio

Документ описывает целевую архитектуру и порядок рефакторинга текущего приложения. Цель — **одно цельное, предсказуемое и быстрое приложение**, а не переписывание с нуля и не бессрочная поддержка старого и нового вариантов одновременно. Каждый этап переносит один набор сценариев на новую границу, проверяет его и затем удаляет замененный код.

## 1. Цель и продуктовая модель

**XMSGi Studio становится приложением и основным рабочим пространством публикаций; Planner — быстрый режим внутри него, а не отдельное приложение.** Оба режима используют одну модель публикации, одни черновики, одну очередь расписания, одну историю, одни аккаунты и одни операции отправки. Переключение режима меняет только интерфейс; оно не монтирует старую страницу, не дублирует состояние и не запускает другой scheduler.

Пользовательский поток должен быть таким:

1. Пользователь выбирает Studio для полноценной подготовки поста: редактор, вложения, форматирование, кнопки, шаблоны и предпросмотр.
2. Пользователь выбирает Planner, чтобы быстро подготовить и отправить или запланировать сообщение.
3. В обоих режимах пост сохраняется в общей модели и попадает в одну очередь/историю. Его можно открыть, продолжить редактировать, перенести или отменить из любого режима.
4. Операции проходят через один application/use-case слой и одну авторитетную реализацию расписания. Renderer не общается с Telegram и файловым хранилищем напрямую.

Это должен быть **модульный монолит**, а не два независимых приложения и не набор микросервисов: одна Electron-сборка, одна точка запуска, единая авторизация и данные, два согласованных UI-режима и четкие внутренние границы. Физическое разделение исходников допустимо только как workspace-модуль без собственной параллельной бизнес-логики и пользовательского runtime.

## 2. Фактическое состояние и архитектурные пробелы

В репозитории уже есть полезные основы, которые следует сохранить и довести до единой системы:

- Electron main/preload отделены от React renderer; IPC payload проверяется, Telegram-сессия и файловые данные остаются в main-процессе.
- `packages/shared/bridge/` содержит типизированный bridge с `BRIDGE_PROTOCOL_VERSION`; `StudioMount` передает Studio scheduler и callback-контракты.
- В `Studio/Studio module` уже есть доменные типы, repositories, publishing/scheduling services, редактор и разделение рабочего пространства на стадии.
- История, черновики, повторные расписания, rich-text, вложения и Telegram-ошибки уже покрыты отдельными тестами.

При этом границы неполны или дублируются:

- Хостовый `src/App.tsx` одновременно собирает состояние приложения, auth, чаты, AI, Planner, Studio callbacks, черновики, историю, маршрутизацию и выбор режима. Это composition root только частично: в нем остается логика нескольких сценариев.
- `src/core/index.ts` является barrel-файлом хуков, а не слоем ядра. Значительная часть бизнес-логики расписания находится в `src/hooks/useScheduler.ts`; в UI также есть `src/pages/SchedulePage.tsx` с крупным смешанным экраном.
- `src/domain/` содержит только `types.ts`; у host нет законченного доменного слоя и согласованной пары repository/application API для своих сценариев. `src/services/` пока мал и не представляет общую application-службу.
- Модели в `src/domain/types.ts`, `packages/shared/types` и `Studio module/src/types.ts` сосуществуют. Некоторые понятия пересекаются (`Post`/`ScheduledMessage`, `Draft`/`SavedDraft`), но не являются одной канонической схемой с явной миграцией.
- Хранение распределено по main JSON stores, `window.draftStorage`, `window.telegram` schedule history, host localStorage и Studio repositories/localStorage. Для одинаковых пользовательских данных не всегда очевидно, какая запись является источником истины.
- Встроенная Studio получает host scheduler через bridge, но `Studio/App.tsx` одновременно создает `useStudioScheduler` fallback. Это два пути поведения; без явного режима они могут разойтись по истории, отмене, ошибкам и повторным отправкам.
- Интеграция Studio зависит от `$studio` alias и специального Vite plugin, разрешающего исходники соседней папки. Это работает в текущей сборке, но не является явным версионируемым package/workspace контрактом.
- `activeAccountId` в host задан как `'account-1'`; в bridge тип ограничен `'account-1' | 'account-2'`. При этом доменная модель уже предполагает аккаунты и принадлежность публикаций аккаунту. Многопрофильность пока не имеет полноценного владельца/выбора в приложении.
- AI/Gemini технически реализован (`useAssistant` → `window.gemini` → preload/IPC → main), но UI ассистента находится в legacy `SchedulePage`; активные `QuickPlannerPage` и Studio не получают этот сценарий. Поэтому рабочий AI-путь не интегрирован в актуальные рабочие места.
- Домен объявляет будущие provider-типы, но фактический транспорт и возможности сейчас Telegram-ориентированные. Абстракцию не следует считать обещанием уже реализованной поддержки других платформ.

## 3. Целевая схема модулей

```text
Electron main
  telegram adapter + IPC handlers + secure/local persistence
                |
Typed preload API / renderer infrastructure adapters
                |
Application use cases (send, schedule, edit, cancel, drafts, history)
                |
Shared domain contracts + validation + normalization
          /                         \\
Studio feature UI                Planner feature UI
(основное рабочее место)         (быстрый режим)
          \\                         /
             единый AppShell
```

Целевая организация исходников после миграции (названия можно уточнить при реализации; ответственность должна остаться единой):

```text
packages/shared/
  domain/        канонические сущности, идентификаторы, статусы, правила
  application/   use cases и порты операций, независимые от React/Electron
  bridge/        версионированные DTO и контракты host <-> Studio
  i18n/          общая локализация
  utils/         чистые общие функции

app/src/
  app/           единственная точка запуска, shell и маршруты
  features/
    studio/      основное рабочее пространство и редактор
    planner/     быстрый режим того же composer/use cases
    drafts/      общие черновики и шаблоны
    schedule/    единственная очередь и действия расписания
    history/     общая история и операции над записями
    accounts/    авторизация, состояние и выбор аккаунта
    settings/    настройки приложения и AI
  application/   use cases и порты
  domain/        канонические сущности и бизнес-правила
  infrastructure/electron/  адаптеры renderer к preload API

packages/shared/
  bridge/        контракты UI <-> host, если граница package остается нужна
  i18n/ utils/   только реально совместно используемые платформенно-независимые модули

main process
  Telegram adapter, защищенные IPC handlers и файловые adapters
  одно активное хранилище каждого вида; старые форматы только для миграции
```

Studio и Planner становятся feature-модулями одного renderer и не импортируют внутренние файлы друг друга. Они используют один application runtime и общие доменные/use-case контракты. Отдельная standalone-сборка Studio не входит в целевую модель, если продуктовая необходимость не подтверждена: оставить второй пользовательский runtime и fallback scheduler означало бы сохранить два приложения.

## 4. Семь этапов перехода к одному приложению

Каждый этап заканчивается работающим приложением. На время миграции допускается временный adapter, но не постоянное сосуществование старого и нового сценариев. После переключения потребителей старый компонент удаляется в том же этапе или в явно названном этапе очистки; нельзя оставлять его доступным через скрытый fallback.

**Основные legacy-пути, которые планируется заменить и удалить после миграции:**

- `src/pages/SchedulePage.tsx` как старый смешанный экран Planner/авторизации/AI. Сначала вынести нужные auth/Welcome Back состояния в единую оболочку, затем удалить страницу и ее page-specific tests/styles.
- Два независимых scheduler-пути: бизнес-логику `src/hooks/useScheduler.ts` перенести в единые use cases с тонкими UI adapters; `Studio/hooks/useStudioScheduler.ts` удалить, если standalone runtime не подтвержден как требование.
- Дублирующие источники черновиков/истории: Planner localStorage draft, Studio fallback repositories и старые schedule-history storage paths. Перенести данные в один owner/repository и удалить старые записи/адаптеры после проверенной миграции.
- Разрозненный набор callback-props и временных refs между `App.tsx`, `StudioMount` и Studio заменить одним версионированным runtime contract; удалить callback-совместимость после перевода всех потребителей.
- Старый AI UI внутри `SchedulePage` удалить. Сам AI оставить только как необязательную capability Studio, если подтверждена польза; иначе удалить также Gemini UI/settings/service в отдельном осознанном решении, а не поддерживать невидимую функцию.
- Старые feature-local types, mapper и alias/build обходы удалять по мере того, как исчезают последние потребители; не сохранять параллельные канонические модели «на всякий случай».

#### Порядок разработки бизнес-логики внутри этапов 2–5

Эту последовательность нужно соблюдать внутри крупных этапов: нижние блоки являются зависимостями следующих. UI Studio и Planner подключаются только после того, как соответствующий use case работает через тестовый adapter.

1. **Контекст аккаунта и адресата.** Стабильный `AccountId`, состояние сессии, загрузка чатов и разрешений. Все последующие данные и операции должны быть привязаны к выбранному аккаунту и target.
2. **Канонический документ публикации.** `PostDraft`: текст, entities форматирования, вложения/Media IDs, inline keyboard, silent/effect и метаданные. Сюда же входят нормализация, лимиты, сохранение и восстановление черновика.
3. **Проверка публикации.** Проверить подключение, существование и доступность target, лимиты Telegram, допустимые типы вложений/markup и совместимость опций до отправки. Ошибки вернуть в общей структуре, пригодной для обоих UI.
4. **Преобразование намерения в команду.** Сформировать одну команду `send now`, `schedule`, `edit/reschedule` или `cancel`; отдельно проверить дату/время/часовой пояс, правила повторения и лимит occurrence. Преобразование schedule date в формат Telegram покрыть чистыми тестами.
5. **Жизненный цикл операции.** Единый use case создает idempotency key, запускает операцию через Telegram adapter, обрабатывает FloodWait/permission/network ошибки и определяет переходы `pending -> scheduled/sent/failed`, retry и cancel. Отложенную доставку продолжает выполнять сервер Telegram, не локальный таймер.
6. **Запись результата и восстановление.** Сохранить подтвержденное/ошибочное состояние, обновить общий upcoming/sent history, восстановить прерванные операции после перезапуска и сверить неоднозначный результат с Telegram, чтобы retry не отправил дубль. Draft и расписание используют repository ports из этапа 2.
7. **Общие проекции и переходы между продуктами.** History, очередь, уведомления и команды «открыть/продолжить в Studio или Planner» читают общий источник данных. Передаются ID и состояние сущности, а не копия отдельной модели.

**Практический порядок переноса:** сначала реализовать пункты 1–2 и repository ports этапа 2; затем пункты 3–6 как application use cases этапа 3; после этого подключить Studio (этап 4) и Planner (этап 5) к тем же use cases. Общую историю и межпродуктовые переходы завершить в этапах 5–6. Не переносить scheduler hook целиком как есть: сначала выделить и протестировать чистые правила/переходы, затем подключить persistence и транспорт.

### Этап 1. Зафиксировать сценарии и границы интеграции

**Большая часть замены:** текущая интеграция `src/App.tsx` → `StudioMount` → `Studio/App.tsx` и набор callback props.

**Что сделать:**

- Зафиксировать сквозные acceptance-сценарии: запуск/выход, выбор чата, создание/сохранение/открытие черновика, немедленная отправка, планирование/повтор, отмена/перенос, запись в историю, открытие поста из Planner в Studio и обратно.
- Снять исходные метрики старта, загрузки основного экрана и Studio, размера renderer chunks и задержки основных действий. Зафиксировать целевые пределы после измерения реальной сборки.
- Сформировать карту текущих владельцев состояния и данных; для каждого поля определить источник истины, потребителя, старое хранилище и миграцию.
- Для каждого найденного старого модуля принять явное решение `keep / replace / delete`; у `SchedulePage`, двух scheduler implementations, каждого draft/history store и standalone Studio должен быть записан конкретный владелец замены и этап удаления.
- Оформить интеграцию как единый typed `ProductRuntime`/application facade, передаваемый продуктовому UI. Вынести из `App.tsx` wiring и адаптацию legacy callbacks в небольшой composition-модуль.
- Зафиксировать DTO, ошибки и правила эволюции протокола в `packages/shared/bridge/`. Сохранить совместимость `protocolVersion: 1` до готовности всех потребителей; новую версию вводить только при несовместимом изменении.
- Зафиксировать, поддерживается ли отдельный standalone runtime. Целевое решение по умолчанию — один embedded runtime; standalone сохранить только при подтвержденном продуктовом требовании и без отдельного scheduler.

**Не делать:** не переписывать Telegram/IPC и не менять формат пользовательских данных в этом этапе.

**Готово, когда:** сценарии воспроизводимы тестами, inventory старых путей имеет решение и этап удаления для каждого элемента, выбран один целевой runtime, а новые метрики зафиксированы для сравнения.

### Этап 2. Каноническая доменная модель и хранилища

**Большая часть замены:** типы `src/domain/types.ts`, `packages/shared/types`, `Studio module/src/types.ts`; repositories и текущие разрозненные localStorage/file-store операции.

**Что сделать:**

- Утвердить канонические сущности: `Account`, `ChannelTarget`, `Post`, `Draft`, `Schedule`, `Media`, `Template`, `HistoryEntry`; определить стабильные ID, `accountId`, статусы, временные зоны и связи между сущностями.
- Развести domain entity и транспортные DTO. Создать явные mapper/normalizer для старых `ScheduledMessage`, `SavedDraft`, `PersistedDraftStore` и shared bridge payload; не переименовывать данные без миграции.
- Определить repository ports для постов, черновиков, расписаний, истории, шаблонов, аккаунтов и вложений. Договориться, что хранится в Electron main, что разрешено хранить как временную UI-настройку, а что нельзя дублировать в localStorage.
- Оставить текущие файловые JSON stores и `safeStorage` в роли реализации портов; добавить schema version, атомарную миграцию, backup/rollback и обработку частично поврежденных данных.
- Перевести потребителей на канонические repositories по одной сущности за раз; временный legacy reader должен быть миграционным кодом с проверкой использования, а не вторым repository в production.

**Готово, когда:** у каждой сущности один канонический тип и ровно один production source of truth; старые записи мигрируют без потери вложений, rich-text, статуса/истории и привязки к чату/аккаунту; после cutover старые writer paths отключены, миграционные тесты покрывают предыдущие форматы.

### Этап 3. Use cases, Telegram adapter и единый runtime операций

**Большая часть замены:** бизнес-логика из `src/hooks/useScheduler.ts`, `Studio/hooks/useStudioScheduler.ts`, services, прямые вызовы `window.telegram`/`window.draftStorage` и разрозненные IPC вызовы.

**Что сделать:**

- Создать платформенно-независимые use cases: `CreateDraft`, `UpdateDraft`, `PublishNow`, `SchedulePost`, `EditScheduledPost`, `CancelSchedule`, `LoadHistory`, `RetryPublish`, `MoveDraftToComposer`.
- На этапе 1 принять явное продуктовое решение о Gemini по реальной пользе. Только если AI оставлен, оформить его отдельным `InterpretPostIntent` use case с типизированными запросом/ответом и Gemini adapter в инфраструктуре. Секреты и вызов провайдера остаются в Electron main.
- Если AI оставлен, сохранять ответ только как предложение: пользователь проверяет и подтверждает его через обычный draft/publish/schedule use case. AI не отправляет и не планирует сообщения сам; уточнение не меняет документ без действия пользователя.
- Перенести в application/domain правила валидации, повторов, idempotency-контекста, нормализации статусов и переходов публикации. UI hooks должны только отображать состояние/вызывать use cases.
- Создать renderer adapter к типизированному preload API. Запретить feature-компонентам прямой доступ к `window.telegram` и `window.draftStorage`; все вызовы идут через адаптеры и use cases.
- Оформить preload как минимальный allowlist API с типами входа/выхода; сохранить проверки источника renderer, валидацию payload и запрет доступа renderer к Node.
- Встроенный Studio и Planner получают одну реализацию publish/schedule/history. Отказ от standalone означает удаление `useStudioScheduler` и его fallback persistence; если отдельный runtime все же подтвержден, он обязан вызывать те же use cases и не дублировать алгоритм.
- Декомпозировать `telegram.cjs`/`main.cjs` только вокруг проверяемых доменных границ (auth, chats, publish, history, account storage); сохранить MTProto поведение и серверное планирование Telegram. Не заменять уже надежный transport ради косметической модульности.

**Готово, когда:** одинаковая операция из Studio и Planner вызывает один use case и дает одинаковый результат; повторный вызов не создает дубль; после переключения UI старые scheduler implementations больше не вызываются и удалены; FloodWait, cancel, retry, restart recovery и ошибки имеют прежние или более строгие гарантии.

### Этап 4. Перестроить Studio как основной рабочий продукт

**Большая часть замены:** `Studio module/src/pages/WorkspacePage.tsx` и связанные стадии/компоненты в `Studio module/src/components/`, плюс `Studio module/src/App.tsx`.

**Что сделать:**

- Превратить `WorkspacePage` в тонкий feature composition: управлять активным сценарием и собирать подэкраны, но не хранить правила публикации, persistence и большой набор несвязанных состояний.
- Выделить самостоятельные feature-модули: composer/document, chat target, attachments/media, rich-text/entities, inline keyboard, schedule/repeat, drafts/templates, preview, history actions.
- Свести редактируемый документ к единой модели `PostDraft`; все стадии работают с ней, а не переносят вручную несвязанные поля message/attachment/entities/options.
- Если AI оставлен по продуктовому решению, подключить его сначала только к Studio через общий assistant use case: передавать минимальный нужный контекст, возвращать предложение/уточнение и передавать выбранный пользователем результат в composer или schedule stage. Если AI не подтверждает пользу, удалить Gemini UI/configuration, а не переносить его ради сохранения кода.
- Передавать публикацию и сохранение через use cases этапа 3. Сохранить текущий Telegram preview, доступность стадий, локализацию и адаптивную раскладку.
- Установить Studio как основной подключенный режим по умолчанию; режим браузерного preview остается явной dev/test-конфигурацией и не меняет пользовательские данные.

**Готово, когда:** компонент страницы не содержит прямой persistence/Telegram логики; каждую большую стадию можно менять и тестировать независимо; создание, сохранение и публикация через Studio проходят end-to-end.

### Этап 5. Перестроить Planner на общие модели и use cases

**Большая часть замены:** `src/pages/SchedulePage.tsx`, `src/components/QuickPlannerPage.tsx` и связанная с ними логика composer/scheduler.

**Что сделать:**

- Разбить Planner на небольшие компоненты/фичи: быстрый composer, выбор адресата, date/time picker, режим повторения и команды над общей очередью. Auth/Welcome Back не часть Planner UI: вынести их в shell/account feature.
- Использовать ту же `PostDraft`, валидацию, media/entity модель и use cases, что и Studio. Planner может иметь более короткий UI, но не собственную модель отправки.
- Не добавлять AI в Planner автоматически. Рассматривать его там только отдельным последующим решением на основе использования AI в Studio; если добавлен, вызывать тот же assistant use case без копии логики и требовать явного подтверждения.
- Сохранить быстрый сценарий как оптимизированное представление общей очереди. Не создавать отдельный набор scheduled/sent данных или независимый алгоритм повторов.
- Реализовать переходы: «продолжить в Studio», открыть draft/scheduled record в Studio и вернуться в Planner без копирования или потери выбранного чата, вложений, форматирования и времени.
- После переноса auth/Welcome Back и всех нужных сценариев удалить `src/pages/SchedulePage.tsx` и его специфичные стили/тесты. `QuickPlannerPage` остается быстрым режимом и использует общие данные; старый экран не должен оставаться запасным production UI.
- Удалить Planner draft/localStorage writer после миграции существующих данных в общий Draft repository.

**Готово, когда:** один и тот же draft открывается и сохраняется из обоих продуктов; операция, созданная в одном режиме, видна и управляется в другом; Planner не содержит второй реализации отправки/планирования.

### Этап 6. Единая оболочка, аккаунты, авторизация и настройки

**Большая часть замены:** хостовый `src/App.tsx`, `src/workspace/AppShell.tsx`, Settings/Auth composition, product-view routing и account context.

**Что сделать:**

- Оставить `App` composition root: загрузка runtime и подключение provider/router. Вынести маршруты и владение состоянием в app-модули; AppShell отвечает за навигацию и общие overlays, а не за продуктовые операции.
- Определить рабочую навигацию Studio ↔ Planner ↔ History ↔ Settings и поведение deep-link/возврата. Studio — основной пункт, Planner — соседняя быстрая команда.
- Ввести реальный `AccountContext`/`AccountId` вместо литералов `'account-1' | 'account-2'`; ограничить область данных аккаунтом, корректно переключать сессии, чаты, черновики и очередь.
- Разделить account lifecycle (connect, sign out, forget, restore) и настройки продукта; централизовать доступ к статусу Telegram и уведомлениям.
- Если AI оставлен, держать его конфигурацию в одном месте Settings и показывать доступность в тех режимах, где функция реально доступна. Если AI удален как невостребованный, убрать неиспользуемые настройки, ключи и UI.
- Сохранить текущие требования безопасности, локализацию ru/en и историю как общую функцию приложения.

**Готово, когда:** UI не создает фиксированный account ID; переключение продуктов не сбрасывает данные; маршруты, logout/forget-account и настройки имеют один владельческий модуль и проверены на повторный вход/перезапуск.

### Этап 7. Удаление legacy-кода, производительность и выпуск

**Большая часть замены:** остаточные legacy storage/adapters, временные bridge compatibility paths, fallback scheduler и standalone entry points; затем оптимизация единой сборки и финальная проверка обновления.

**Что сделать:**

- Провести миграцию пользовательских данных в канонические repositories с резервной копией, schema version, идемпотентностью миграции и диагностикой результата. Не удалять исходные данные в той же транзакции, в которой впервые создается новая запись.
- Удалить legacy reader/writer и storage keys после подтвержденного cutover и успешного обновления существующего профиля. Оставить только версионированную миграцию, необходимую для поддержки пользователей предыдущих версий.
- Удалить старую callback compatibility, fallback scheduler и standalone entry point при выбранной единой embedded модели. Проверить поиском по репозиторию, что старые компоненты, ключи и импорты больше не используются.
- Сделать Studio feature частью одного приложения/workspace build, без отдельной продуктовой оболочки и дублирующей инициализации. Сборка и упаковка должны работать из чистого checkout.
- Повторить замеры этапа 1: старт и первый экран не должны загружать тяжелый Studio chunk до запроса пользователя; Studio загружается по требованию, без блокировки Planner. Оптимизировать только измеренные узкие места; не добавлять memoization/слои без профилирования.
- Проверить доступность AI в Studio только если capability оставлена продуктовым решением; AI не должен быть условием запуска или публикации.
- Обновить архитектурную документацию, IPC reference и инструкции разработки; удалить устаревшие описания числа каналов/границ, если они расходятся с кодом.

**Готово, когда:** нет старой страницы Planner, неиспользуемых scheduler/storage paths, callback legacy и параллельной production-модели; чистая установка и обновление с предыдущей версии сохраняют данные; тесты, typecheck, lint, renderer build и Electron packaging проходят; метрики скорости не регрессировали и основные пользовательские сценарии остаются предсказуемыми.

## 5. Порядок и контроль качества

Рекомендуемый порядок: **1 → 2 → 3 → 4 → 5 → 6 → 7**. Это семь крупных этапов; каждый разбивается на маленькие вертикальные PR. Новый путь становится единственным сразу после проверенного cutover, но удаление формата данных/мигратора откладывается до подтвержденной совместимости с обновлением. Этапы 4 и 5 используют один domain/application contract.

Для каждого этапа:

- Сначала добавить characterization/contract tests на существующий путь, затем переключать один вертикальный сценарий за раз.
- Использовать короткий переход `legacy adapter -> canonical port -> новый consumer`; на этапе переключения убрать старый writer/UI/scheduler. Оставлять только узкий read-only migrator для старых данных и удалить его, когда закончится заявленный срок совместимости.
- Проверять React tests для измененной фичи, Node tests для main/storage/IPC, Studio module tests, typecheck обеих частей и build. Для релизного этапа дополнительно проверять packaging на поддерживаемых платформах.
- Не считать тест одного UI достаточным для гарантии планирования: проверить повторный schedule, отмену/редактирование, FloodWait, перезапуск в промежуточном статусе, миграцию и отправку Telegram через соответствующий тестовый слой.
- Сохранять инварианты: Telegram сам выполняет отложенную доставку; секреты остаются в main/safeStorage; renderer вызывает только allowlisted preload API; повторная операция идемпотентна; Studio и Planner показывают одинаковую историю.
- Сравнивать замеры запуска/загрузки с baseline, а не объявлять приложение быстрым по субъективному ощущению; не загружать Studio до необходимости и не держать две копии общих данных в памяти.

## 6. Результат

После рефакторинга пользователь видит одно XMSGi Studio. Внутри него есть полноценный Studio workspace и быстрый Planner, но нет старой Planner-страницы, второго scheduler, второго production-хранилища или самостоятельной версии приложения. Общие данные и use cases делают переходы между режимами надежными; измеренная загрузка по требованию и отсутствие дублирующей работы делают приложение быстрее и понятнее.
